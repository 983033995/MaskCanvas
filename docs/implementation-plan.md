# MaskCanvas 实施计划 v2

更新：2026-10-22。用户已授权开始迭代开发。0.1 已实现本地核心与基础入口；各阶段实际状态与证据见 [development-progress.md](development-progress.md)。本表保留目标退出条件，不能把部分实现等同于阶段全部通过。

## 本次优先级修订

常规交接由 ZIP 改为 JSON；下一阶段先做“Agent 建议草稿 → 编辑器供人调整 → 服务端记录确认 → Agent 续跑”，先跑一个客户端的真实闭环，再扩展自动分割与双后端。字段、已实现部分与验收见 [agent-workflow.md](agent-workflow.md)。旧表中的便携包作为历史计划，不再是主要交互。

## 目标与决策原则

实现需求文档中的三模式、双后端、精确合成、跨 Agent 接入和数据交接。先验证会影响产品形态的风险，再确定画布复用范围和工期。选最简单的可验收实现，不先做多用户、通用图层系统或插件市场。

## D1 必须回答的问题

1. InpaintCanvas 能否接现有 Qwen 编辑工作流和可用的 GPT 编辑接口？其后台浏览器依赖、全分辨率导出与 Windows 侧桥接是否适合？
2. 能否明确取得 edit/keep/context mask 与原图坐标？保护语义是否需要独立合成器补齐？
3. GPT 路线的实际模型名、mask、参考图、返回尺寸、账号与费用是否可用？不能凭节点登记判定。
4. 8GB GPU 下不同 crop 的耗时与显存是多少？和 H3 共用队列时，查询/取消/恢复是否隔离？
5. Agent 视觉和分割能力如何提供？严格本地模式是否需要额外服务？

候选优先外部适配。直接派生上游 GPL/AGPL 代码前检查许可证，与本仓库 MIT 的关系必须明确。

## 测试策略

- 确定性测试先覆盖 mask 运算、坐标、合成、保护差分与版本冲突。
- 模拟后端测试覆盖异步状态、断线恢复、取消与幂等。
- 真实后端用非私人合成照片，记录实际输入、工作流、模型和产物。
- 美学与身份验收采用原尺寸局部加全图；程序约束和视觉结果分开报告。
- 端到端测试必须包括人画标注、Agent 建区、自主任务和包移交。
- 不对未经明确允许的照片执行远端观察或生成。

## 风险与停止条件

| 风险 | 应对 |
|---|---|
| 模型改变脸型、移动主体或产生双轮廓 | 拒绝自动接受；记录候选，回到范围/上下文/来源检查 |
| 无法兼顾保护区和无缝边缘 | 明确约束冲突；人工调整范围，不偷偷修改保护对象 |
| 第三方服务超时且不知是否已受理 | 恢复查询；不自动换模型/新会话重复生成 |
| 现成画布无法满足 headless/大图/版本语义 | 保留其执行适配价值；仅补齐必要自有模块 |
| 本地分析能力缺失 | 人工标注可继续；自主识别状态明确为不可用 |
| 共享 GPU 正在运行其他任务 | 排队和显示已知状态；不抢占、清空队列或全局 interrupt |
| 专业色彩需求超出 sRGB 首版 | 保留原始文件，单列后续能力，不静默降级 |

## 待进一步确认但不阻碍本轮设计

默认建议：先面向个人 Mac 控制端 + Windows GPU；自然精修为默认任务，造型改造需明确指定；私人照片默认本地处理，远端分析与生成分别允许。以上为设计假设，不冒充已经确认的用户偏好。
